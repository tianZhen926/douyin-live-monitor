> **仅供学习交流。** 本项目用于研究 Python 网络请求、轮询状态机、消息通知和网页交互，不作为生产服务提供，不承诺监控准确性、通知及时性或持续维护。

## 项目介绍

一个使用 Python 3 标准库编写的多主播直播状态监控示例。后端、网页和交互脚本集中在一个文件中，无需安装第三方 Python 依赖或运行前端构建工具。

可以通过阅读代码学习：

- HTTP 请求、JSON 解析和环境变量配置。
- 轮询任务、开播与下播状态判断、异常后的状态衔接。
- JSON 文件持久化、并发锁和原子替换。
- 微信服务号模板消息与 Server酱通知的基本接入。
- 原生 JavaScript 看板、拖拽排序、响应式布局和 FLIP 动画。

```
app.py                 # 程序和内嵌网页
deploy/                # systemd 与 nginx 配置示例
```

## 示例功能

**监控与推送**

- 输入直播间链接、房间号或抖音号即可添加主播；粘贴主播主页链接（含 `MS4wLj` 的 sec_uid 链接）会明确报错并提示改填抖音号。
- 状态机五态：`live` / `offline` / `ended` / `unknown` / `error`。
- 开播推送、下播推送（含本场时长）、连续 N 次检测失败的异常告警与恢复通知。
- 推送渠道自动选择：配置齐了微信服务号四个参数就走模板消息，否则走 Server酱，都没配则只出看板不推送。

**场次记录**

- 每场完整「开播 → 下播」写入 `sessions.json`，记录标题、起止时间、时长、在线人数峰值，可导出 CSV。
- 场次起止时间优先使用平台返回值，获取不到时使用检测时间；记录不等同于官方完整统计。

**看板**

- 卡片带头像、昵称、标题、在线人数、粉丝数与地区，每卡可进入直播间、立即重检、删除。
- 拖拽排序（Pointer Events，触屏可用）+ 「手动排序 / 开播优先」两种排序模式，顺序分别存服务端和浏览器。
- 场次记录面板可收起/展开，宽屏下切换列数时卡片做位置与宽度的补间动画。
- 自适应到手机宽度；`prefers-reduced-motion` 下关闭动画。

## 本地学习运行

需要 Python 3。在项目目录执行：

```bash
python3 app.py
```

浏览器打开 `http://127.0.0.1:8080`。不配置推送参数时仅展示看板；添加主播前请先确认使用权限。

服务默认仅监听本机，程序本身没有身份认证，不要将端口直接暴露到公网。不要在公共演示中展示个人主播列表、场次记录或推送凭据。

## 配置（全部走环境变量）

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `SENDKEY` | 空 | Server酱 sendkey，微信参数不全时的备用推送渠道 |
| `WX_APPID` / `WX_APPSECRET` / `WX_TEMPLATE_ID` / `WX_OPENID` | 空 | 微信服务号模板消息四个参数，四个都非空才启用 |
| `DASHBOARD_URL` | 空 | 推送里带的看板链接，不填则退回直播间链接 |
| `POLL_INTERVAL` | `60` | 轮询间隔秒数，下限 15 |
| `ALERT_AFTER_FAILS` | `5` | 连续失败几次后推异常告警，下限 2 |
| `PORT` / `BIND` | `8080` / `127.0.0.1` | HTTP 监听地址 |
| `ROOMS_FILE` / `SESSIONS_FILE` | 同目录 | 主播列表与场次记录的落盘路径 |
| `DETAIL_TTL` / `DETAIL_RETRY` | `21600` / `600` | 粉丝数、地区等慢变化字段的刷新与重试间隔 |

凭据只从环境变量读取，代码和仓库里没有任何密钥。生产环境建议用 systemd 的 `EnvironmentFile=` 指向一个 600 权限的文件。

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 看板页面（前端内嵌在 `app.py` 里） |
| GET | `/api/rooms` | 全部主播状态快照 + 轮询间隔 + 推送渠道 |
| GET | `/api/sessions?room=&limit=` | 场次记录，默认 50 条，磁盘上最多保留 2000 条 |
| POST | `/api/rooms` | 添加主播 |
| DELETE | `/api/rooms/<web_rid>` | 删除主播 |
| POST | `/api/rooms/<web_rid>/check` | 立即检测某个房间 |
| POST | `/api/order` | 保存卡片顺序 |
| POST | `/api/test-push` | 发一条测试推送 |

## 实现要点

**两个接口分工**：实时状态（是否开播、标题、在线人数、头像）走直播间 enter 接口；平台返回的场次起止时间、粉丝数、地区走 reflow 接口。为减少请求，reflow 只在场次变化或刷新、重试间隔到期时调用。

**空响应不覆盖已知值**：平台在降级响应里会把昵称/头像/标题返回成空串，直接写回会把已有数据抹掉，所以这些字段一律 `新值 or 旧值`。

**场次边界不能被错误吃掉**：轮询失败时状态是 `error`，如果按"上一轮状态"判断边界，一次风控就能让整场直播的下播记录、场次落盘、历史行一起消失。现在额外持久化一个 `last_status`，所有边界判断都基于最后一次成功检测到的状态，进程重启后也能接上。

**并发落盘**：抓快照和写盘在同一把锁内完成，否则周期保存可能拿到旧顺序、却比用户拖拽排序后更晚写盘，把用户刚排好的顺序覆盖回去。所有 JSON 写入都是 `tmp` + `os.replace` 原子替换。

**时区固定 CST**，不依赖宿主机时区。

**前端无框架无构建**：全部逻辑在一个内嵌 `<script>` 里，动画用 FLIP（记录旧位置 → 改布局 → 从旧值弹到新值），弹簧曲线由欠阻尼解析解采样成 CSS `linear()`，不支持时退回贝塞尔。拖拽期间和面板动画期间冻结重绘，避免轮询打断动画。

## 已知局限

- **会被限流。** 高频请求会让出口 IP 拿到空响应或直接挂起（本项目单次 HTTP 超时 15 秒）。被限流时表现为卡片报"监控异常"、头像或场次缺失。这是这套实现方式的固有风险，不是 bug。
- **轮询是单线程顺序的。** 一个房间卡住会让整轮变慢，房间数多时更明显。刻意保持简单，没有拆成并发。
- **峰值观众只是采样最大值。** 精度取决于接口返回值；例如 `1.2万` 会转成 `12000`，`10万+` 会转成 `100000`，不保留加号。两次采样之间或监控未运行时的高点可能遗漏，因此不等于官方完整统计；在线峰值也不是累计观看人数。
- **不支持完整历史回补。** 场次记录依赖检测到的状态变化；重启时可利用已保存的状态衔接，但无法恢复停机期间所有遗漏场次。
- **没有测试套件。** 开发期用的是打桩脚本，仓库里没有 `tests/`，改动需要自己在测试环境验证。

## 部署学习参考

`deploy/` 用于学习服务管理和反向代理配置，不是完整的安全部署方案。远程访问应配置 HTTPS、身份认证或受控网络访问，并保护环境变量文件。目录下包含：

- `douyin-monitor.service` —— systemd unit，凭据走 `EnvironmentFile=/etc/douyin-monitor.env`（这个文件不进仓库）。
- `nginx.conf.example` —— 反代到 `127.0.0.1:8080` 的最小配置。**示例里没有认证**，公网暴露前务必自己加 `auth_basic` 或源站白名单，否则任何人都能往你的服务器里加主播、触发你的推送。
